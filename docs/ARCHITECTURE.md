## Request flow today (Free mode)

Everything happens in the browser. The server only serves pages.

The app's one working screen is `/workspace` (`app/workspace/`). `/` is the landing page (`app/_components/Landing.tsx`): one sentence on the product, a recorded real run (`data/example-run.json`, recorded through OpenRouter by `scripts/record-example-run.mjs` with the workspace's own client, similarity and `StandardConsensus` code; `lib/exampleRun.ts` derives the score and level with the workspace's mapping), the three ways in (`/workspace?start=keys`, `/workspace?start=local`, Pro shown as coming soon), what the score means and how a run works. The root layout is a server component so pages can export metadata (text in `lib/siteMetadata.ts`, one `layout.tsx` per public route); its client side is `app/_components/RootShell.tsx`. `/features` and `/about` follow the claims rule and link to `/benchmarks`. The old wizard routes redirect into it with the matching part open (`lib/workspaceRoutes.ts`, other query parameters kept): `/config` opens the settings sheet (`?panel=settings`), `/ensemble` opens the model picker (`?panel=models`), `/prompt` focuses the question (`?panel=prompt`) and `/review` shows the workspace with the last run. `_components/Workspace.tsx` puts the component library's `AppShell` (header, history sidebar), `Composer`, `ConsensusPanel` and `AnswerColumns` together; the app hooks in `app/workspace/hooks/` feed them from the store. `hooks/useWorkspacePanel.ts` reads `?panel=` and drops it when the settings sheet closes. Below 1024 px, while answers stream, `_components/RunResult.tsx` shows one status row in place of the agreement and consensus cards, so the first answer is on the first screen; the cards return once every answer is in.

1. Settings (`_components/SettingsSheet.tsx`, opened from the header or the first-run setup card): the user enters provider keys (`hooks/useApiKeySettings.ts`). `store/slices/apiKeySlice.ts` encrypts them with AES-GCM through `shared-utils/security` and Zustand persists them to localStorage (`ensemble-ai-store`). The same sheet adds OpenAI-compatible endpoints (Ollama, LM Studio, llama.cpp, vLLM, OpenRouter, Groq, Together or a custom URL), kept in `store/slices/endpointsSlice.ts` with their optional keys encrypted the same way. Each endpoint is checked with `GET {baseURL}/models` when added or edited, and again on page load when a local server lacked its embedding model or the server could not be reached or was blocked by the browser (`hooks/useEndpointConfiguration.ts`). It also holds the embeddings provider for the agreement score, theme and language (`AppearanceSettings`), and clearing the data kept in the browser. One valid key or one connected endpoint is enough to start, so a user with only Ollama needs no cloud key; until then a setup card under the composer says what to add. On a first visit (nothing stored, `onboardingDone` unset, no `?panel=`), or when the landing page sends `?start=keys|local` and nothing works yet, `hooks/useOnboarding.ts` opens the `OnboardingSheet` (`_components/WorkspaceOnboarding.tsx`): own key, local models or Pro (coming soon). The key field picks the provider from the key's prefix (`lib/keyProvider.ts`); an OpenRouter key adds an OpenRouter endpoint, any other key goes through `useApiKeySettings`, so it is encrypted and checked by the same code as settings and the result shows inline. The local path shows the Ollama offer from `useOllamaDetection` and the connected server. Start, Skip, closing or going to settings set `onboardingDone`. On first run (no endpoint, offer not dismissed) `hooks/useOllamaDetection.ts` looks for Ollama and the `OllamaDetectedNotice` molecule offers to add it with one click, under the composer and in settings (see Local model servers below).
2. Composer (`hooks/useWorkspaceComposer.ts`): the user writes the question (the draft is kept in the store) and picks up to 6 models in the inline picker. It offers the models of providers with a valid key, from `lib/models.ts` (hard-coded fallback) merged with live lists from `lib/providerModels.ts`, and the models of connected endpoints, read live from each server (`lib/endpointModels.ts`) and grouped by endpoint (`lib/workspaceModels.ts`). The method menu lists `standard | majority | elo | council` with the calls and cost range of each (`hooks/useRunEstimates.ts`, see Pricing below) and picks the summarizer (the first model when none is chosen; a preset saved without one loads with none). With Ranked (`elo`) chosen, it also sets how many of the best answers are merged (`eloTopN`, 3 up to the number of answers). The options menu adds an answer by hand (`_components/ManualAnswerDialog.tsx`) or saves the models, method and summarizer as a preset (`_components/SavePresetDialog.tsx`, `ensembleSlice.saveEnsemble`; the same name replaces the earlier one). Presets are listed, loaded and deleted in the history sidebar. The curated `PRESETS` in `lib/ensembleConstants.ts` are not shown yet.
3. Asking (`hooks/useWorkspaceRun.ts`, which wires the hooks below):
   - `hooks/useStreamingResponses.ts` starts the run: `responseSlice.startRun` clears the previous run and records its prompt and its models (`runModels`), so editing the ensemble afterwards never changes the run on screen (`selectRunModels`; runs stored before `runModels` use the selection). It gets a client from `ProviderRegistry` and calls `streamResponse` for each model. Each stream buffers its own chunks and flushes them to the store every 100 ms. A stream writes to the store only while it is the latest one for its model in the run it was started for (`runStartedAt`), so a stream left over after New question or a newer run is ignored.
   - A failed model does not fail the run. Clients report a `ProviderError` with a kind (`invalid_key`, `missing_key`, `rate_limited` with the provider's retry delay, `timeout`, `provider_unavailable`, `other`), stored on the answer. Its card explains the error and offers a retry for that model only (`ResponseErrorNotice` in `AnswerCard`). Agreement and consensus use the answers that succeeded, and `_components/RunExclusionNote.tsx` names the models left out, or explains that consensus needs at least 2 answers. A retry clears the consensus, and drops the result of a consensus still running, so it runs again with the new answer. Asking again drops a consensus still running for the old run.
   - The last run is persisted in localStorage (`ensemble-ai-store`) and is shown again after a reload or a later visit to the workspace (or `/review`). Nothing is requested again on load. An answer that was still streaming when the page unloaded is loaded as an `interrupted` error with a retry button. Past runs are kept in IndexedDB in Free mode (database `ensemble-ai-history`, store `runs`, newest 200 kept; `lib/runHistory.ts`). `hooks/useRunHistory.ts` writes the run on screen once no answer is streaming and writes it again as its agreement and consensus arrive (`lib/runHistoryRecord.ts` maps the store to a record: prompt, models, method, summarizer, answers, manual answers, embeddings, agreement score and level, consensus, consensus usage and cost). The history sidebar lists the stored runs by the time they started (`responseSlice.runStartedAt`), plus the run on screen while it is not stored yet; its search matches the prompt, the answers, the consensus and the model names. Opening a run puts it back on screen read only: `responseSlice.historyView` is set, so no embeddings, consensus or retries are requested, manual answers cannot be added, the consensus shows the method and summarizer it was run with, and `_components/HistoryRunNotice.tsx` says so above the result. Asking a question from there starts a new live run. Deleting the run on screen clears the workspace. Clear data in settings also empties the history.
   - `hooks/useRunState.ts` picks the embeddings provider with `lib/embeddingsProvider.ts`: the user's choice in settings when its key is valid, otherwise OpenAI, then Google, then an OpenAI-compatible endpoint with an embedding model (`lib/endpointStatus.ts`). `hooks/useResponseEmbeddings.ts` calls `generateEmbeddings` on that provider for each answer. `responseSlice.calculateAgreement` builds the cosine similarity matrix with `shared-utils/similarity`, and `lib/agreement.ts` turns it into pairwise comparisons, matched to answers by the embeddings' model ids so a failed embedding leaves that answer out (the agreement card names it) rather than blanking the score. Stored embeddings carry the provider that produced them, so a reload reuses them instead of calling the provider again. `lib/workspaceRun.ts` maps all this to the `AgreementSummary` card: pending with progress while answers arrive, the score with each pair, or why there is none (no embedding model, with a link to settings and the exact `ollama pull` command when a connected Ollama has none; the embedding calls failed; fewer than 2 answers). Manual answers are embedded and scored with the model answers (`useRunAnalytics` returns them as `agreementAnswers`). A manual answer added during or after a run joins it and clears the consensus so it runs again over every answer (`hooks/useAddManualAnswer.ts`). New question in the sidebar drops the run and its manual answers (`hooks/useNewQuestion.ts`), so they never reach the next prompt's consensus or agreement score. The high, medium and low labels use cut-offs for the embedding model in use from `data/agreement-calibration.json` (`lib/agreementCalibration.ts`, fitted by `ensemble-eval calibrate-agreement`). A model with no fitted entry keeps the original (cosine + 1) / 2 mapping (high above 0.8, medium from 0.5) and the card marks the labels uncalibrated. No model is calibrated yet.
   - `hooks/useConsensusGeneration.ts` runs the chosen consensus strategy with the summarizer model. Each provider it hands to a strategy is wrapped with `withUsageTracking`, which records the tokens of every consensus call in `responseSlice.consensusUsage`.
   - Majority runs call `MajorityVotingConsensus.runConsensus`. One structured call to the summarizer (`generateStructured`) extracts each answer's short final answer (number, option letter, yes/no or short phrase). The answers are normalised (number formats, case, punctuation, option letters) and counted. A single winner with at least 2 votes becomes the consensus text (a numeric winner as its canonical value, so `1/2` gives `0.5`) and no other call is made. On a tie, when fewer than half the answers are short, or when extraction fails, the strategy falls back to the LLM method (ranking call, then synthesis). The outcome is stored in `responseSlice.majorityVote` and shown by the `MajorityVoteBreakdown` molecule in the consensus card: each answer with its votes and models, the winner or tie, and why the fallback ran.
   - Once every answer has finished, the consensus card's footer shows the cost of the run (`hooks/useRunCost.ts`): answers, consensus calls and embedding calls priced with the shared table. It updates as consensus calls finish.

Embeddings: OpenAI uses `text-embedding-3-small` and Google uses `gemini-embedding-2`. OpenAI-compatible endpoints use the embedding model set on the endpoint (for example `nomic-embed-text` on Ollama) through `requestOpenAICompatibleEmbedding`. The other providers have no embeddings API and throw `EmbeddingsNotSupportedError`; nothing falls back to fake vectors outside mock mode. Mock mode keeps the mock client's deterministic hash vectors.

## Pricing

`packages/shared-utils/src/pricing/` (import `@ensemble-ai/shared-utils/pricing`):

- `priceTable.ts` is generated by `npm run prices:refresh --workspace=packages/shared-utils`, which reads the public OpenRouter model lists (`/api/v1/models` and `/api/v1/embeddings/models`, no key) and maps OpenRouter ids to our provider and model ids (`x-ai` becomes `xai`, Anthropic `claude-opus-5.5` becomes `claude-opus-5-5`, `:batch` and `:free` variants are dropped). Prices are USD per million input and output tokens.
- `getModelPrice(provider, modelId, table, endpoints)` returns `{ status: 'unknown' }` for a model with no entry. For `openai-compatible` it calls `getEndpointModelPrice` (`endpointPrices.ts`), which finds the endpoint named in the model id among the configured endpoints (`{ id, baseURL }`, passed in by `useRunEstimates` and `useRunCost`). An endpoint is local only when its preset is local (Ollama, LM Studio, llama.cpp, vLLM) and its base URL is loopback (`localhost`, `*.localhost`, 127.0.0.0/8 or `::1`; `isLocalEndpoint`). Local endpoints cost 0 and are marked `local`. OpenRouter at `openrouter.ai` is priced when the table has an entry with the same OpenRouter id. Everything else is unknown: a local preset pointed at another host (it may be a paid or shared server), a Custom endpoint even on localhost (it may proxy a paid API), Groq and Together (the table holds OpenRouter prices, not theirs), and endpoints not passed in. Nothing guesses a price; the UI lists unpriced models and leaves their calls out of the cost. `estimateRun` and `computeRunCost` count priced, unpriced and local calls (`localCallCount`), so `RunCostSummary` shows a lower bound ("at least") when some calls have no price, "unknown" when none has, and says how many calls ran on local models at no cost. Unpriced calls are never shown as $0.00; $0.00 appears only when every priced call is local.
- `estimateRun` counts calls per consensus method, matching the strategy packages: standard 1, majority 1 to 3 (the extraction call, plus ranking and synthesis when the vote falls back), ELO `N*(N-1)` judge calls plus 1 summary, council `N*(N-1)` critiques, `N` rebuttals, `N*(N-1)` judgments, up to `N*(N-1)/2` ranking calls and 1 summary (56 for 5 models). ELO and council need 3 answers. Embeddings add one call per answer. The cost range assumes short (200 token) to long (2000 token) answers. These assumptions live in `pricing/tokenAssumptions.ts`; a fit from recorded benchmark usage in `pricing/tokenCalibration.ts` replaces them when one is committed (none is yet).
- The price table keeps open-weight vendors (Meta Llama, Qwen, Mistral, Microsoft, IBM Granite, NVIDIA, AllenAI) under `openrouter/<OpenRouter id>`, so their models are priced when called through OpenRouter.
- After a run, `computeRunCost` prices each call. Providers pass input and output tokens to `onComplete` as a fourth `usage` argument when their stream reports them (OpenAI, xAI, DeepSeek, Gemini, Anthropic, Perplexity), and return them as `usage` from `generateStructured`. Hidden reasoning tokens count as output: xAI leaves them out of `completion_tokens`, so output is taken as `total_tokens - prompt_tokens` when that is larger. When a provider reports none, tokens are estimated from text length (4 characters per token) and the cost is labelled estimated. Embedding calls are always estimated.

## Providers

- Interface: `AIProvider` in `shared-utils/src/providers/types.ts` (`streamResponse`, `generateEmbeddings`, `validateApiKey`, `listAvailableModels`, `listAvailableTextModels`, `generateStructured`).
- `ProviderName`: `openai | anthropic | google | xai | deepseek | perplexity | openai-compatible`. `ProviderMode`: `mock | free | pro`. The same union is in `consensus-core/src/types.ts`.
- Clients live in `shared-utils/src/providers/clients/<provider>/`. All extend `base/BaseFreeClient.ts` (key check, stream timeout of 120 s by default, configurable per call with `timeoutMs`, and error classification through `errors/providerError.ts`).
  - OpenAI, xAI and DeepSeek use the `openai` SDK; the last two set a fixed `baseURL`.
  - Anthropic uses `@anthropic-ai/sdk`. Google uses `@google/generative-ai` plus axios.
  - `openai-compatible` uses `fetch` (see the next section).
  - Perplexity calls the Agent API (`POST https://api.perplexity.ai/v1/agent`) with `fetch`, because Sonar Chat Completions ended on 2026-09-27. Its model ids (`perplexity-fast`, `perplexity-low`, `perplexity-medium`) are Agent API effort presets. Old `sonar*` ids still map to a preset. Key validation uses the free `GET /v1/models`.
  - The SDK clients set `dangerouslyAllowBrowser: true`.
  - Per-model request rules: Anthropic models from Opus 4.7 on (including all 5.x models) get no `temperature`, and structured output uses `output_config.format` instead of a forced `tool_choice`, which Opus 5.5 and Sonnet 5.5 reject (`clients/anthropic/anthropicModelRules.ts`). OpenAI models whose default reasoning effort is above `none` (o-series, `gpt-5`, GPT-5.5 and later, GPT-6) get no `temperature`; base `gpt-5.1` and `gpt-5.2` default to `none` and keep it (`clients/openai/openAIModelRules.ts`).
- `factories/createProviderClient.ts` switches on provider and mode. `pro` throws "not yet implemented". `openai-compatible` in Free mode needs a `getEndpoints` callback instead of `getApiKey`.
- `registry/ProviderRegistry.ts` is a singleton keyed by provider and mode. The app registers clients in `app/src/providers/index.ts`.

### OpenAI-compatible endpoints

Design, as built for M2:

- One provider name, `openai-compatible`, covers every endpoint. Several endpoints can be configured at once. Each model id is qualified with its endpoint id, `${endpointId}/${modelId}` (`ollama/llama3.2:3b`, `openrouter/meta-llama/llama-3.1-8b-instruct`), and parsed on the first slash. So selections, saved ensembles, consensus, persistence and pricing keep working on `(provider, model)` pairs with no new field.
- Endpoint ids are the preset id, then `${presetId}-2` and so on (`clients/openaiCompatible/endpointPresets.ts`), so the preset can be read back from any model id. Whether an endpoint is local also needs its base URL (see Pricing above), since the user can point any preset at any host. Presets: Ollama `http://localhost:11434/v1`, LM Studio `http://localhost:1234/v1`, llama.cpp server `http://localhost:8080/v1`, vLLM `http://localhost:8000/v1`, OpenRouter `https://openrouter.ai/api/v1`, Groq `https://api.groq.com/openai/v1`, Together `https://api.together.ai/v1`, and Custom (base URLs checked against each project's docs in November 2026).
- `FreeOpenAICompatibleClient` talks to one server with `fetch`, so no Authorization header is sent when the key is empty and no SDK headers trip a local server's CORS rules. It lists every model from `GET {baseURL}/models` unfiltered, streams chat completions with `stream_options.include_usage` for usage, embeds through `requestOpenAICompatibleEmbedding`, and classifies errors with `classifyProviderError`. `generateStructured` tries `response_format: json_schema`, then `json_object` (schema in the prompt), then plain text, and extracts the JSON object from the reply (bare, fenced or embedded in prose). A 400, 422 or 501, or a reply that is not JSON, moves to the next format; key, rate limit and server errors do not.
- `OpenAICompatibleEndpointsClient` is the registered `openai-compatible` client. It reads the connected endpoints from the store at call time and routes each call to the endpoint named in the model id. Embeddings use the first connected endpoint with an embedding model. The app passes an endpoint's embedding model on only when the last check found it in `GET /models` (Ollama's `:latest` tag matches either way), so a preset's suggested `nomic-embed-text` that was never pulled does not cause a 404 for every answer; the endpoint card says the model is missing instead.
- Store: `endpointsSlice` keeps `{ id, presetId, label, baseURL, apiKey, encryptedApiKey, embeddingModel, status, error, errorCode, modelCount, embeddingModelFound }` per endpoint, and `ollamaOfferDismissed`. Only `encryptedApiKey` is persisted (`sanitizeEndpointsForPersist`); the root layout decrypts it with `initializeEndpointKeys`. `apiKeys` stays keyed by the six key providers (`ApiKeyProvider`).
- UI: the `EndpointConfiguration` organism in the workspace's settings sheet (one add button per preset, a link to the local models guide, one `EndpointInput` per endpoint with base URL, optional key, embedding model (`EndpointEmbeddingField`), status and a Local badge shown only for a local preset at a loopback URL), the `EndpointLogo` atom for preset logos, a server icon for the provider in `ProviderLogo`, and family logos (Meta, Qwen, Gemma, Mistral and others) in `ModelLogo`. Strings are in the component library's EN and FR locale files, including the Custom preset name and the check failures that have no server message (`errorCode`).
- Mock mode: the mock client has three `ollama/...` models. In mock mode every endpoint connects without a request and offers those models under its own id.
- The server (`providerService.ts`, `routers/provider.ts`) does not serve endpoints; they are configured in the browser only.

### Local model servers

- Detection: `detectOllama` (`shared-utils/.../openaiCompatible/localServers.ts`) probes `GET {url}/api/tags`, then `GET {url}/v1/models`, with a 1.5 s timeout per probe, and never throws or logs; anything that does not answer with a model list is "not found". It splits chat models from embedding models (`isEmbeddingModelId`) and picks an embedding model (`pickEmbeddingModel`). The app probes `NEXT_PUBLIC_OLLAMA_URL`, default `http://localhost:11434` (`lib/localModels.ts`). Mock mode never probes.
- When to probe: a page on a loopback origin (the local run, or dev) probes on load and shows nothing when Ollama is absent. A hosted page probes on load only when the browser already grants `loopback-network`; otherwise it offers a "Look for Ollama" button, so Chrome's and Firefox's local network prompt follows a click. That check uses a 30 s timeout, since the request waits for the user's answer to the prompt; a real click on Allow has not been tested (headless browsers cannot answer the prompt). The button is hidden from users who have a valid key (also when one turns valid later) or denied the permission.
- Blocked calls: `checkEndpoint` (`lib/endpointValidation.ts`) maps a fetch `TypeError` (no HTTP answer) to the `unreachable` error code, or to `localBlocked` when the endpoint is on loopback and the page is not (`isLocalNetworkBlockLikely`). `EndpointInput` then shows `LocalServerHelp`: why browsers block it, and the `npm run local` command with a link to the guide.
- Embedding model: when the check finds the endpoint's embedding model missing, it returns `suggestedEmbeddingModel` from the server's list. `useEndpointConfiguration` applies it to a local endpoint whose field is empty or still the preset's suggestion, and never to hosted endpoints or a model the user typed. With Ollama and no embedding model, `EndpointEmbeddingField`, the Ollama offer and the agreement card's unavailable state show the exact `ollama pull` command (`ollamaEmbeddingPullCommand` in `lib/endpointStatus.ts`).
- Local run: `npm run local` (`packages/app/bin/ensemble-local.mjs`, helpers in `scripts/localRun.mjs`) builds the workspace when there is no standalone build, when the build was not made by `npm run local` or comes from another git commit (checked against the marker `.next/standalone/.ensemble-local.json`, since `NEXT_PUBLIC_MOCK_MODE` is fixed at build time), or with `--rebuild`, copies static files and `public/` next to the standalone server, and runs it on `127.0.0.1` (port 3000 or `--port`). The browser findings that make this the recommended path are in [LOCAL_MODELS.md](./LOCAL_MODELS.md).

Adding another hosted OpenAI-compatible service is one entry in `ENDPOINT_PRESETS`, an icon in `EndpointLogo.tsx`, and, if it should be priced, a host-specific rule in `getEndpointModelPrice` (the table only holds OpenRouter prices).

Adding a provider with its own API and key touches about 20 files: shared-utils `types.ts`, `createProviderClient.ts` and `MockProviderClient.ts`; `consensus-core/src/types.ts`; app `providers/index.ts`, `lib/ensembleConstants.ts`, `app/workspace/hooks/useApiKeySettings.ts`, `store/slices/apiKeySlice.ts`, `ensembleSlice.ts` (`ProviderType`), `store/index.ts`, `lib/models.ts`, `lib/modelModalities.ts`, `lib/providerStatus.ts`, `app/workspace/hooks/useConsensusGeneration.ts`, server `providerService.ts` and `routers/provider.ts`; component-library `ProviderLogo.tsx`, `ModelLogo.tsx`, `ModelSelectionList.tsx` (provider groups), `ResponseCard.tsx` (`PROVIDER_NAMES`), and the i18n JSON files. A provider with embeddings also touches `selectEmbeddingsProvider.ts` and `EmbeddingsProviderSelector.tsx`.

## Server today

- tRPC 11 at `/api/trpc/[trpc]`. Routers in `app/src/server/api/routers/`:
  - `auth` (`me`)
  - `provider` (`listTextModels`, `streamText`, `streamTextEvents`), using server keys from `src/env.js` through `server/providers/providerService.ts`. `streamText` buffers the whole answer. Cancellation is a no-op.
  - `post` (leftover T3 demo).
- `protectedProcedure` verifies a Firebase ID token with Firebase Admin (`server/auth/firebaseAdmin.ts`). The client has no sign-in code yet, and no UI calls any tRPC procedure.
- Sentry is configured (`sentry.*.config.ts`). No database. No Stripe.

## Hosting today

- Firebase App Hosting, backend `ensemble-app` (`firebase.json`), configured by `apphosting.yaml`: 1 vCPU, 1 GiB, `minInstances: 0`, `maxInstances: 3`. With a minimum of 0 nothing is billed while idle; the first request after a quiet spell pays a cold start.
- `infra/terraform/` creates the Firebase project, App Hosting backend (id `ensemble-app`, matching `firebase.json`), APIs, IAM and GitHub Workload Identity.
- `.github/workflows/deploy.yml` deploys on push to `main`, then runs a free HTTP smoke check of the deployed URL (`/` and `/workspace` answer 200, following redirects; `/config` redirects to `/workspace?panel=settings`) and one Google-only E2E test (when `TEST_GOOGLE_API_KEY` is set). The full `free-mode` suite runs only on a manual dispatch with `full_e2e`.
- `.github/workflows/eval-ci.yml` (paid evals) runs only on manual dispatch or on PRs labelled `run-eval`.

## Eval harness

- Datasets load from Hugging Face in `eval/src/lib/benchmarkDatasetLoaders.ts`: gsm8k, math500, truthfulqa, gpqa, mmlu_pro, simpleqa, hle, arc, hellaswag.
- Models are given as `provider:model`, `<endpoint>:model` for OpenAI-compatible presets (`openrouter:qwen/qwen3-14b`, `ollama:llama3.2`) or `compat:<baseURL>#<model>` (`eval/src/lib/modelSpecs.ts`). Keys come from the environment (`OPENROUTER_API_KEY` and so on); local servers need none. Defaults are in `eval/src/lib/evalDefaults.ts`: `google:gemini-3-flash-preview`, which matches the committed caches in `eval/.cache/`.
- New runs use the structured answer protocol (`eval/src/lib/methodology.ts`): multiple-choice options shuffled with a fixed seed (the permutation is recorded), a structured final answer through `generateStructured` with `json_object` and `Final answer:` fallbacks, and mechanical scoring, so only SimpleQA and HLE need an LLM judge. A judge must differ from the generators unless `--allow-same-judge` is set. The committed caches are scored with the legacy protocol (unshuffled, LLM judge for every dataset) because their replies answered the old prompts.
- Errors and timeouts count as wrong and are reported separately, including failed responses that the committed single-baseline caches left unscored. Real runs default to 200 questions per dataset. `quick-eval` output and `analyze` reports have 95% Wilson intervals and paired McNemar tests (`eval/src/lib/pairedStats.ts`); the `compare` and `ci-eval` regression report does not yet.
- Concurrency: AIMD limiter in `eval/src/lib/concurrencyPool.ts`.
- Cost per answer and per consensus call comes from the shared price table, using reported token usage or a text-length estimate (`costFromTextLength`). Local models cost $0. A total that includes unpriced calls is shown as a lower bound or as unknown, never as free. Judge calls are not priced.
- Benchmark matrix (`eval/src/lib/matrix/`, `eval/bench/matrix.json`): `npm run bench:matrix --workspace=packages/eval` runs three open models alone and as an ensemble (mechanical majority and standard consensus) plus a cached premium reference on GSM8K, MMLU-Pro, GPQA and TruthfulQA. It prints a cost estimate from the price table first and spends only with `--yes`, resumes from its own results, and writes `eval/results/<run-id>/` with a `summary.json` (accuracy, Wilson intervals, McNemar p-values against the best single model, cost). `--publish` copies the summary to `app/src/data/benchmark-summary.json`, which the `/benchmarks` page reads. A mock run is never published there, and the page hides a mock summary outside development. `report/generate_figures.py --results <run dir>` builds the report figures from it.
- Calibration: `calibrate-agreement` fits per-embedding-model agreement cut-offs from answer pairs labelled by their mechanically read final answers, into `app/src/data/agreement-calibration.json`. `calibrate-tokens` fits `estimateRun`'s token assumptions from the usage each response records, into `shared-utils/src/pricing/tokenCalibration.ts`. Both refuse to write those committed files from mock results.
- Still open in M3: no paid matrix run yet, so no results, calibrations or report figures from it are committed. Method and formats in `packages/eval/docs/BENCHMARKS.md`; the rest in `packages/eval/docs/architecture.md`.
